# ADR 0011: Journaled manual guided capture

- **Status:** Accepted locally; host-verified and corrected exact Pixel 6 checkpoint passed
- **Date:** 2026-09-05
- **Scope:** Task 15A manual capture, selected-reference presentation, safe Stop, and startup settlement

## Context

Task 14 established separate reducer, Room, app-private file, and restart-recovery authorities. The started-session route could reach a rear-camera preview, but it still displayed a fixed demo reference and could not send a manual shutter request through those authorities. Directly calling CameraX and then writing Room state would allow a crash, duplicate callback, route exit, or partial burst to split physical files from logical ownership.

## Decision

The started-session route owns one `GuidedCameraViewModel` for the exact validated Room snapshot. It restores the pure reducer's current pose, attempt counter, and applied receipts, then loads the current validated reference landmarks and decoded inference dimensions from the same transactional bootstrap projection.

Startup recovery runs before a `Ready` bootstrap can admit the camera. Cleanup completes through the Task 14B.3 path. An attempt whose three files are already `FINAL_DURABLE` is confirmed and advanced through the existing journal-derived Room transaction. An outstanding recovery result blocks the bootstrap read and exposes the existing repair state.

One serialized coordinator handles a manual reducer command in this order:

1. Register the exact attempt and its three journal rows, then mark the attempt started.
2. For ordinal 0, 1, and 2, advance Room to `WRITING_TEMP` before reserving paths or invoking CameraX.
3. Sync and hash the exact temporary output, persist `TEMP_SYNCED`, admit `FINAL_RENAME_PENDING_SYNC`, publish through the owned reservation, sync the directory, and persist `FINAL_DURABLE`.
4. Return durability to the reducer. The reducer emits the confirmation effect, and Room atomically derives three immutable private outputs, applies one receipt, advances once, creates one deterministic export intent with three outputs, and consumes the transient journal rows.
5. Load the next selected reference only after Room returns applied or exact replay.

Duplicate CameraX callbacks are ignored after the first terminal callback for a write. An expected failure settles through Room and exact recovery before the UI becomes retryable or finishes a requested Stop. Unexpected adapter or authority failures complete as reconciliation-required instead of leaving the route indefinitely busy. The route defers Back/Stop while an accepted capture or confirmation is still in flight. Resource leases keep Room and the capture executor alive until terminal callbacks release them.

The visible overlay and uncalibrated match diagnostics both use the current Room-selected reference. Automatic capture remains disabled. The manual Capture action bypasses only match/lock eligibility and always requests the same three-output reducer protocol.

## Consequences

- A successful manual request has one logical attempt, exactly three deterministic durable private files, one confirmation receipt, and one sequence advance.
- A process restart cannot admit a new camera session while exact cleanup or ready-to-confirm work remains unresolved.
- The UI never receives app-private paths, byte hashes, provider identifiers, or Room entities.
- Stop can leave the active Room session resumable, while an ambiguous attempt remains blocking on the next entry.
- MediaStore execution, physical deletion, speech, automatic shutter, match calibration, TalkBack acceptance, and full end-to-end hardware acceptance remain separate work.

## Verification boundary

Host tests cover reducer restoration, selected-reference parsing, exact cross-adapter ordering, duplicate callbacks, failure settlement, startup confirmation, safe Stop, resource leasing, and route admission. A generated-data Android test composes the reducer, real Room V4 authority, exact app-private publisher, deterministic generated bytes, journal-derived confirmation, and one advance without opening the camera or accessing personal media. A second compile-verified method uses the real rear camera through that same coordinator and confirms one advance; it requires a separately authorized final-artifact Pixel 6 checkpoint because it creates three transient app-private photos. The first live run proved that CameraX's file-target API replaces its destination inode, which the journal correctly rejected. The production writer now uses an already-open output stream and closes it before durability validation so the admitted inode remains stable.
